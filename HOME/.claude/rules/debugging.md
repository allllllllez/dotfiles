# Debugging

## 保留を宣言する前に、自分が作ったものを見る

「原因不明」「保留」「エスカレーション」を口にする前に、対象オブジェクトの
定義を 1 回は取得する（`DESC` / `SHOW` / `show` コマンド / 設定ファイルの実値）。

外部要因（プラットフォーム側の反映待ち、既知の障害）を先に疑って待機に入る前に、
自分が設定した内容が意図どおりかを確認する。待機は最も高価な診断手段である。

エスカレーション先に渡す根拠は、渡す前に自分で再検証する。
誤った根拠は相手の診断を誤らせる。

## 「無い」と結論する前に、仮説の外側を見る

「X は取得できない」「原因は Y だ」と結論する前に、調べた範囲が自分の仮説の内側に
閉じていないかを確認する。絞り込み検索が空振りしたことは、対象が存在しないことの
証拠にならない。

対象の全体を機械的に列挙できる手段があるなら、仮説に合わせた検索より先にそれを実行する。
設定ファイルなら全キーの列挙、対象システムなら操作履歴や監査ログ。

手元のログに無いことを、対象システムに無いことと混同しない。プラットフォーム側の
履歴機能（クエリヒストリ、監査ログ、実行履歴）は一次情報であり、手元のログより優先する。

## 免責を書く前に、手元の手段を確認する

「未検証」「確証がない」「動くかは不明」と書こうとしたら、書く前に
その不確実性を自分で閉じられないかを確認する。

確認する対象は4つ。利用可能な skill の一覧、対象ツールの公式ドキュメント、
成果物を読み戻して実地確認する手段、そしてリポジトリが用意している一括検証
ターゲット（Makefile、package.json の scripts、CI 設定）。いずれかで閉じられるなら、
免責ではなくタスクとして実行する。

検証コマンドを自分で列挙しそうになったら、その前に一括ターゲットの有無を調べる。
個別に列挙すると必ず取りこぼし、Cru が後から1つずつ追加依頼することになる。

同じ免責を2回以上書いたら、それは免責ではなく未着手のタスクである。
相手が「やって」と言わない限り着手しない扱いにしない。

閉じられないときだけ免責を書く。そのときは、何を試して閉じられなかったかを
1行添える。
