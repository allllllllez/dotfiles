# README Documentation Style

適用範囲: リポジトリの README.md。
[[writing-structure]]（チャット応答・実務ドキュメント、ですます調）や
[[writing-technical]]（書籍原稿、である調）とはレジスタが異なる。
READMEはコマンド・コード・箇条書き中心の簡潔なnotation styleで書き、
文体（ですます/である）の統一よりも短さと構造の分かりやすさを優先する。

## デバッグ経緯・トラブルシューティング節を作らない

- preview featureのフラグ名の根拠、ライブラリのバグ、内部挙動の発見経緯など、
  作業中に分かったことを「既知の懸念点」「Tips」のような独立した節にまとめて残さない。
- ユーザーが実際に知る必要がある制約は、該当するコード定義や手順のすぐ近くに
  一言で埋め込む。単独の節を新設しない。
- 実務上必要な追加操作（例: target_lagがあるので手動REFRESHが要る）を見つけたら、
  「懸念点」として書き添えず、手順の中に1ステップとして組み込む。

## 概要は最終状態だけを2〜3文で

- 「当初Xだったが、Yという理由でZに変更した」という経緯を書かない。
- 今何を作り、何を作らないか（スコープの境界線）だけを事実として述べる。

## 各手順の説明文は徹底的に短く畳む

- 「〜なので、〜は〜してしまう。そのため〜する。」のような因果の長文にしない。
- 「〜と同じく〜を使うと(問題)。代わりに〜で実行。」くらいまで切り詰める。
- 説明済みの理由を繰り返すときは「〜と同様の理由で」で済ませ、再度理由を書かない。
- 文末は「〜する。」より「〜。」で体言止め・省略気味に切ることがある
  （例:「INSERT INTOで実行する。」→「INSERT INTOで実行。」）。

## 表の下に補足説明の段落を続けない

- フォルダ構成表などのMarkdown表は、各セルの一言で完結させる。
- 「なぜこの配置が必要か」のような設計背景の説明を表の下に段落で追加しない。
  必要ならコードコメント等、別の文脈に譲る。
- [[writing-structure]]の「表の直後に1〜2文で結論を書く」規則とは矛盾しない。
  短い結論文は書いてよい。ここで禁じているのは、設計背景・経緯を長く説明する段落。

## 機能単位で`###`サブセクションに分割し、目次もネストする

- 話題が異なるなら（例:「事前準備」の中の`.env`と`parameters`）、
  フラットな箇条書きではなく`###`で分けて、目次も子項目として反映する。
- 「作るもの/作らないもの」のような対比も同様にサブセクション化する。

## 独立した運用操作は手順の連番から外し、独立した見出しにする

- 「後始末（destroy等）」のような、通常の構築手順とは別ライフサイクルの操作は、
  番号付き手順の最後に埋め込まず、`## 後始末`のような独立した見出しにする。
- コマンド例は必要最小限のフラグだけを見せる。検証時に使った全フラグを律儀に残さない。

## コードブロックにファイル名を注記する

- 設定ファイルの中身を見せるときは ` ```ini:.env ` ` ```csv:database_schema.csv ` のように
  言語+ファイル名の注記を付ける。
