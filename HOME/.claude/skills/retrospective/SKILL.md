# Retrospective

セッションの進め方で得た学びは、セッションが閉じると消える。次のセッションは同じ手戻りを繰り返す。
振り返りの目的は反省ではない。次のセッションの挙動を変える変更を rules / skills に置くことである。

## いつ使うか

- 実装や調査が一区切りついた時点
- 手戻りが目立ったセッションの直後
- 同じ指摘を複数回受けた自覚があるとき

使わない場面:

- 単発の質問応答、5往復未満のセッション。subagent を1本使うので割に合わない
- 振り返るより先に直すべき不具合が残っている状態。先に直す
- コードの書き方の学び。それは `/learn` の担当

## 材料の取得

### 対象ファイルの特定

```bash
ls -t ~/.claude/projects/"$(pwd | sed 's|/|-|g')"/*.jsonl | head -1
```

cwd の `/` を `-` に置換したものがディレクトリ名。mtime が最新の JSONL が実行中のセッションにあたる。

見つからないときは Cru にパスを尋ねる。推測で別セッションを振り返らない。

### 抽出

このファイルは数百 KB になる。生読みは親も subagent も禁止する。
explorer subagent を1本起動し、jq で絞ってから読ませる。

抽出対象:

- 依頼と訂正（Cru の実発言のみ）

  ```bash
  jq -r 'select(.type=="user" and (.isSidechain != true)) | .message.content
         | if type=="string" then . else (.[] | select(.type=="text") | .text) end' "$F"
  ```

  `type=="user"` のレコードは大半が `tool_result` である。`.message.content` を素で取ると
  ツール結果が全件混ざり、避けたいコンテキスト膨張がそのまま起きる。
  `string` と `text` ブロックに絞ることで実発言だけが残る。

- ツール呼び出しの列

  ```bash
  jq -r 'select(.type=="assistant") | .message.content[]?
         | select(.type=="tool_use") | .name' "$F"
  ```

  名前と対象パスのみ。入力全文は取らない。

- 失敗の痕跡: `.toolUseResult` のうちエラーと非ゼロ終了
- 同一ファイルへの複数回編集
- Cru の否定・訂正の語（違う、そうじゃない、やめて、戻して、指摘）

subagent に返させるのは「依頼 → 実行 → やり直し」の事実の時系列と、やり直しが起きた箇所の一覧だけ。
評価と KPT の分類は返させない。それは親の仕事である。

compact が走ったセッションでも JSONL には全記録が残る。コンテキストから消えた序盤も材料に入る。

### 材料の欠落

JSONL を読んでも埋まらない穴がある。振り返りの冒頭で、読み取れなかった区間を申告する。

- Cru が口に出さなかった不満は記録に残らない
- subagent の要約は非可逆に情報を落とす
- 会話の外で起きた判断（別ターミナルでの手作業など）は見えない

## グラウンドルール

Norm Kerth の Prime Directive を出発点に置く。

> Regardless of what we discover, we understand and truly believe that everyone did the best job they could, given what they knew at the time, their skills and abilities, the resources available, and the situation at hand.

運用規則に落とすと、原因の追究はしても責任の追及はしない。
これは分析を甘くする規則ではなく、追究の対象を人から判断に移す規則である。
「Cru の指示が曖昧だった」は責任の追及。「曖昧なまま着手した」は判断の追究。後者だけを扱う。

もう1つ、コントロール外の話題を扱わない。
モデルの限界、ツールの速度、外部サービスの障害は議題にしない。
扱うのは指示の出し方、確認の取り方、委譲の判断、rules の書き方に限る。

## 進行

0. 実行フォルダの `.claude/rules/` と `.claude/skills/` を読む。
   今セッションでそれらが守られたかを確認する。守られなかったものは Problem の候補。
   これが前回の Try のレビューにあたる（定着先がそのまま記録になっている）
1. explorer subagent を起動し、事実の時系列を取得する
2. Keep を挙げる。うまくいったことと、それを支えた具体的な振る舞い。
   「スムーズだった」で済ませず、何がスムーズにしたのかを書く
3. Problem を挙げる。手戻り、待ち、誤解、指摘を受けた点。
   subagent が返したやり直し箇所は全件、Keep か Problem のどちらかに分類する。未分類を残さない
4. Problem に「なぜ」を掘る。回数は固定しない。
   打ち切りの判定は「特定した原因を直して、この問題はまだ起こりうるか」。Yes ならもう一段掘る。
   原因は複数あるのが普通なので、最初の1つで止めない
5. Try を出す。1〜3件を上限とする。
   各 Try は具体・観測可能・次セッションで実行可能にし、実行主体（Claude 側 / Cru 側）を明記する
6. 各 Try の定着先を振り分ける
7. 変更提案として提示する。ファイルへの書き込みは y/n の確認を取ってから行う

Try を3件に絞るのは妥協ではない。振り返りのアクション完了率は計測で 40〜50% に留まり、
件数を増やすと1件も実行されなくなる。

## 定着先の振り分け

| 定着先 | 対象 | 判断基準 |
|---|---|---|
| `.claude/rules/*.md` | 毎回守るべき行動規範 | 適用範囲が広く、手順を持たない。ファイル種別で絞れるなら `paths` frontmatter を付ける |
| `.claude/skills/*/SKILL.md` | 手順のある再利用可能な作業 | 起動条件が言えて、複数ステップがある |
| 定着させない | そのセッション固有の事情 | 一回性である。同じ状況が再来しない |

「定着させない」を毎回検討する。全 Try をルール化すると、rules/ が誰も守らない箇条書きの山になる。
既存ルールに追記できるなら新規ファイルを作らない。

## 提示フォーマット

```
## 材料

対象セッション: <jsonl のパス>
読み取れなかった区間: <なければ「なし」>

## Keep

- <続けたいこと> — <それを支えた具体的な振る舞い>

## Problem

- <困ったこと> → <なぜを掘った結果の原因>

## Try

| Try | 実行主体 | 観測方法 | 定着先 |
|---|---|---|---|
| <具体的な行動> | Claude / Cru | <次セッションで何を見れば守られたと言えるか> | <パス、または「定着させない」> |

## 変更提案

### <対象パス>

<追記・変更する文面>
```

## Red flags（合理化に注意）

| 出てくる合理化 | 実態 |
|---|---|
| 「特に問題なくスムーズだった」 | Problem を探す努力を放棄している。やり直しは必ず記録に残っている |
| 「Cru の指示が曖昧だった」 | 責任の追及。曖昧なまま着手した側の判断を掘る |
| 「モデルの制約なので仕方ない」 | コントロール外に逃げている |
| 「コンテキストに残っている分で十分」 | subagent を省略した手抜き。序盤が抜ける |
| 「Try を5件出せた」 | 3件を超えると1件も実行されない |
| 「今回の学びは一般化できる」 | 一回性のものをルール化しようとしている。再来するかを問う |

## よくある失敗

- **愚痴で終わる**: Problem の列挙で止まり、原因にも Try にも到達しない
- **Try が抽象的**: 「コミュニケーションを改善する」は実行できない。観測方法が書けないなら Try ではない
- **実行主体が空**: 「両者で」に割り振ると誰も実行しない。1人を名指しする
- **既存 rules/skills を確認しない**: 前回の Try が守られたかを見ないと、同じ Try を出し続ける
- **コントロール外を議論する**: 自分たちで変えられない要因に時間を使う
